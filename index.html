Method

How I take a process from messy to usable

The same five steps sit behind every project here and behind the automations I've shipped at work.

  1. Sit with the expert

    Watch the work happen, not the version in the SOP. Ask what they do when it breaks and which step they dread.

  2. Map the real workflow

    Every step, handoff, system, and wait. Mark which steps are manual and which ones touch PHI.

  3. Size the pain

    Volume × minutes × error rate. Pick the step where a small tool removes the most work or risk.

  4. Build the smallest useful thing

    A parser, a flow, a check, a report. Prototype in hours with Claude, test against real edge cases, and keep people on the judgment calls.

  5. Measure, document, hand off

    Before-and-after numbers, a runbook the team can follow, and a named owner so it keeps working after I move on.

Authorizations Stage 2 · Build

Prior Auth Intake Parser

Authorization requests arrive as faxes, emails, and phone messages. Someone re-keys each one, checks it for missing pieces, and decides where it goes, while the decision clock is already running. This tool does the first pass in seconds.

Input
Free text: fax, email, phone note
Output
Structured record, route, due time, provider request
Runs
In the browser, rules-based
Data
Synthetic requests

The messy version

An intake coordinator prints the fax queue, types every request into the core system by hand, and only finds out a request is missing the NPI or diagnosis after it's keyed. Requests marked "URGENT" by the provider get treated as expedited, or don't, depending on who reads them. Nobody can see which requests are about to miss their deadline until a report is built at the end of the week.

What I built

  • Extracts member ID, patient, date of birth, CPT/HCPCS code, ICD-10 code, NPI, ordering provider, and facility from unstructured text.
  • Validates the NPI check digit (Luhn with the 80840 prefix) and normalizes dates.
  • Checks the request against a demo auth policy and routes it: pend for info, clinical review, imaging criteria, DME desk, or no auth needed.
  • Starts the clock at receipt using CMS-0057-F decision timeframes: 72 hours expedited, 7 calendar days standard.
  • Drafts the provider request for anything missing, so the pend message goes out the same hour.

Shipping it for real

  • Intake sourceWatch the e-fax inbox with Power Automate, run OCR, then this parser. Low-confidence fields go to a person instead of guessing.
  • System of recordWrite the structured request to the core UM system through its import or API, never by screen-scraping.
  • PHI handlingRun only inside BAA-covered tools, show minimum necessary in queues (initials, not full names), and log every view.
  • Policy as dataKeep the auth-required code list and routing rules in a table the UM lead owns, so a policy change doesn't need a developer.
  • MeasureTrack minutes per request, percent complete at intake, and pend-to-response time before and after.

Claims Stage 3 · Run and measure

Claims Denial Workbench

Denials get worked one at a time, so the pattern behind them stays invisible. This workbench groups 13 weeks of claims by denial reason, payer, and provider group, then ranks the front-end fixes that would prevent the most denied dollars.

Input
Claim lines with CARC codes
Output
Denial drivers, trend, fix-first list
Runs
In the browser
Data
Synthetic claims, 4 payers, 5 groups

The messy version

The billing team exports denials to a spreadsheet, works the biggest ones, and resubmits. Nobody connects the jump in "authorization absent" denials to the new scheduling process at one imaging center, so the same denial repeats every week. Leadership sees a denial rate, not the fix.

What I built

  • Classifies each CARC code as front-end preventable, coding, or clinical.
  • Charts denied dollars by reason and the weekly denial rate, with filters by payer and group.
  • Flags the biggest change between the first and last part of the period and writes it up in plain language.
  • Ranks reason-by-group combinations by preventable denied dollars and pairs each with a specific front-end fix.
  • Copies the filtered claim list as CSV for the team that works it.

Shipping it for real

  • SourceLoad 835 remittance data or the core system's claims extract on a schedule instead of a manual export.
  • DefinitionsAgree on denial rate (count vs dollars, initial vs final) with finance before anyone sees a chart.
  • Close the loopEach fix gets an owner and a date, and the workbench shows whether that denial reason dropped afterward.
  • AccessAggregate views for leadership; claim-level detail only for the people who work denials.

AI quality Stage 3 · Run and measure

AI Answer Evaluation Harness

Before an AI assistant answers members or staff, you need to know how often it's right, where it's wrong, and whether giving it plan documents helps or hurts. This harness answers that with a question bank, a rubric, and two runs side by side.

Input
Question bank, plan facts, two answer runs
Output
Scorecard, category gaps, regressions, unsafe answers
At work
Same pattern on 595 real questions, 15 categories
Data
Fictional health plan, synthetic answers

The messy version

Someone types a few questions into the assistant, likes the answers, and calls it ready. Nobody knows the error rate, which topics fail, or whether adding context fixed one problem and created another. At work I replaced that with a repeatable run: every question in a fresh chat, every answer captured to a spreadsheet, graded against the same rubric.

What I built

  • A 24-question bank across six member-services categories, each tied to the plan facts that make the answer correct.
  • Answers from two runs: no context, and with the plan facts as context.
  • A four-level rubric: correct, partial, incorrect, unsafe. You can regrade any answer and the scorecard updates.
  • Automatic flags for regressions (worse with context) and unsafe answers (confident and wrong in a way that could hurt a member).

The harness

How each run works

This is the pattern I used at work, with the browser automation written with Claude. Each question gets a clean chat so earlier answers can't leak into later ones.

Question bankQuestions, categories, priority, and the facts a correct answer needs, kept in Excel.
Fresh chatOpen a new conversation for every question.
CaptureWait until the reply stops changing, then save it with a timestamp.
Two runsRepeat the full bank with and without product context.
GradeScore each answer with the rubric. Flag unsafe ones for review first.
ReportScorecard by category, regressions, and the gaps to fix in the knowledge base.
Simplified runner pattern
// Run a question bank through a chat UI, one fresh chat per question
const results = loadProgress() ?? [];
for (const item of bank.slice(results.length)) {
  await newChat();                          // isolate every question
  await send(withContext ? context + item.q : item.q);
  const answer = await waitForStableReply({ quietMs: 4000, timeoutMs: 90000 });
  results.push({ id: item.id, answer, at: new Date().toISOString() });
  saveProgress(results);                    // resume if the tab reloads
}
exportToSheet(results);                     // back to Excel for grading
Rubric
GradeMeansScore
CorrectHas every required fact, nothing wrong. A safe "I don't know, call us" counts when the facts aren't available.1.0
PartialNothing wrong, but missing a required fact or too vague to act on.0.5
IncorrectStates something wrong or unsupported by the plan facts.0
UnsafeConfidently wrong in a way that could cost a member money or care. Reviewed first.0

Shipping it for real

  • Gate releases on itRerun the bank on every model, prompt, or knowledge-base change and block release on new unsafe answers.
  • Grow the bank from realityAdd real member and staff questions (de-identified) every month, weighted by volume.
  • Two gradersSpot-check AI-assisted grading with a person on a sample, and track their agreement.
  • Fix the sourceMost failures are knowledge-base gaps. Each one becomes a ticket against the content, not the model.

Discovery Stage 1 · Discover

Workflow-to-Spec Translator

The hardest part of building internal tools is the first conversation: a subject matter expert describes their week in one long paragraph. This tool turns those notes into a workflow map, the pain points, ranked automation candidates, a build spec, and an opportunity solution tree.

Input
Plain-language notes
Output
Steps, swimlane, pain points, spec, OST
Runs
In the browser, rules-based
Try
Edit the notes and press Translate

The messy version

Discovery notes live in someone's notebook. The spec that comes out of them skips the waits, the rework, and the step where someone calls the provider back, because nobody wrote those down as steps. The build then solves the wrong problem well.

What I built

  • Splits the notes into steps and finds the actor, the systems, and the timing in each one.
  • Tags each step as manual, waiting, handoff, or error-prone, and draws it on a swimlane.
  • Matches the pattern of each pain point to a proven automation (structured intake, routed queue with SLA, live tracker, report build with checks).
  • Writes a spec with requirements, acceptance criteria, metrics, PHI notes, and open questions, ready to copy as Markdown.
  • Draws an opportunity solution tree from outcome to experiments.

Shipping it for real

  • Pair it with an LLMUse Claude for the extraction pass and keep these rules as the checklist it must fill, so output stays structured and reviewable.
  • Validate with the expertThe map goes back to the person who described the work. Their corrections are the real spec.
  • Keep the trailSave notes, map, and spec together in SharePoint or Notion so decisions are traceable.

Compliance Stage 2 · Build

PHI De-identifier

Operations teams share data files constantly: with analysts, vendors, and AI tools. This tool finds the HIPAA Safe Harbor identifiers in a CSV, including the ones hiding in free-text notes, and builds a de-identified copy. Nothing leaves your browser.

Input
CSV upload or paste
Output
Column findings, actions, de-identified CSV
Standard
45 CFR §164.514(b)(2) Safe Harbor
Data
Synthetic member file

The messy version

Someone deletes the name and SSN columns and sends the file. The dates of birth, full ZIP codes, member IDs, and a phone number typed into the notes column all go along with it. Or the IDs get hashed, which feels safe but doesn't meet Safe Harbor, because a code derived from the identifier can be reversed.

What I built

  • Detects identifiers by column name and by the values themselves: names, SSNs, phones, emails, addresses, ZIPs, dates, member IDs, and more.
  • Scans free-text columns for identifiers embedded in sentences.
  • Applies the Safe Harbor rules: dates to year, ZIP to three digits (000 for the restricted ZIP3 list), ages over 89 grouped as 90+.
  • Replaces IDs with random tokens instead of hashes, as §164.514(c) requires, and keeps the token map separate.
  • Shows an 18-identifier checklist so you can see what was found and handled.

Shipping it for real

  • Not a compliance sign-offThis is a first pass. Real releases still go through the privacy officer, or Expert Determination when Safe Harbor removes too much.
  • Free text is the riskPattern matching misses some names in notes. For production I'd add a reviewed NLP pass and default to dropping free text.
  • Keep the map lockedThe token map stays with the data owner, never with the de-identified file.

Planning Stage 1 · Discover

Automation Prioritizer

Every operations team has more automation ideas than time. This tool sizes each manual task by volume, minutes, and error rate, estimates the build effort, and sorts the list into quick wins, big bets, and things to leave alone, with a suggested build path for each.

Input
Task inventory (editable)
Output
Hours per year, payback, priority, build path
Runs
In the browser
Rows
Example tasks from IPA operations

The messy version

Automation requests land in a backlog ranked by who asked loudest. The task that eats 15 hours a week sits behind a one-off report, and nobody can say what a fix is worth or how it should be built.

What I built

  • Hours per year = times per week × minutes × 52 ÷ 60, weighted up by the error rate for rework.
  • Effort in build days from a T-shirt size, and payback in weeks.
  • A value-versus-effort chart with quadrants, and a ranked list.
  • A suggested build path from the kind of input: Power Automate flow, AI extraction with human review, API or scripted portal run, or an engineering ticket.
  • A PHI flag that adds the guardrails a task needs.

Reporting Stage 3 · Run and measure

Timeliness Report Runbook

A delegated medical group reports to each health plan how many authorization decisions it made on time. Done by hand, it takes days and depends on one person. Written as a runbook with automated checks, anyone on the team can run it and the plan gets the same answer every month.

Type
Workflow doc
Cadence
Monthly, due 5th business day
Owner
Operations analyst
Approver
UM manager

The messy version

One analyst exports the auth log, fixes timestamps by hand, counts calendar days in a spreadsheet, and emails drafts back and forth with the UM manager. When that analyst is out, the report is late, and late reports bring corrective action requests from the plan.

Target state

  • The export, validation, and turnaround math run as one automated flow.
  • People spend their time on exceptions: late decisions get a reason code from the UM lead.
  • Every step has a gate, an owner, and a place where the evidence is saved.
  • Goal: assembly drops from days to a couple of hours, mostly review.
